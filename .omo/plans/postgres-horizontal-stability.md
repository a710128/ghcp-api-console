# postgres-horizontal-stability - Work Plan
## TL;DR (For humans)
Replace the three local SQLite databases with a clean minimal-state PostgreSQL 16 deployment, while retaining existing HTTP API DTOs. `proxy` becomes a horizontally scalable API service behind Traefik; PostgreSQL advisory locks make token initialization/refresh single-flight across replicas. `login` becomes an API producer plus exactly one `pg-boss` worker, so browser-login work survives an API or worker restart without horizontally scaling Playwright. The plan adds aggressive short-TTL cleanup, graceful shutdown, readiness, and integration coverage, but deliberately has no backup subsystem or historical request-stat store.

This deliberately starts with empty PostgreSQL state: it includes no SQLite import, dual write, historical backfill, Redis, Kubernetes manifests, or changes to public OpenAI/Anthropic-compatible endpoints. It requires PostgreSQL 16 (PostgreSQL 13 is the minimum supported by `pg-boss`), one Compose host, and an internal Docker network. Console administrator state remains the existing `ADMINS_FILE`/`admins.json` file on its `console-data` volume; it is deliberately not migrated to PostgreSQL.

Estimated execution: architecture-scale. Main risks are changing persistence semantics, job cancellation/retry behavior, and ensuring no service uses its legacy local files after cutover. Mitigate through an isolated PostgreSQL integration stack, contract tests, staged Compose smoke testing, and an explicit rollback limited to reverting the new empty-state deployment before real accounts are provisioned. PostgreSQL volume loss is accepted and requires account/token reprovisioning.

## Scope
In scope:
- A shared PostgreSQL-only persistence architecture for `proxy`, `sso`, and `login`.
- Drizzle SQL migrations, pooled `pg` access, PostgreSQL health checks, and a test-only PostgreSQL environment.
- `pg-boss` durable login jobs, exactly one login worker process, retry/dead-letter policy, and encrypted durable credentials.
- PostgreSQL-backed cross-replica coordination for proxy token work and SSO SCIM throttling.
- Traefik-routed Docker Compose deployment, proxy replicas, worker services, bounded Docker/application logs, short-TTL DB retention, graceful shutdown, readiness, and metrics.

### Login Execution Topology
- Deploy exactly one `login-worker` process with `LOGIN_WORKER_CONCURRENCY=1`. Login browser automation is intentionally not horizontally scaled.
- PostgreSQL/`pg-boss` remains the durable queue and restart-recovery mechanism, but a multi-worker identity-lock/worker-lease protocol is out of scope.
- Task generation, account credential version fencing, and durable pending result write-back remain mandatory because sequential stale tasks can still overwrite newer credentials.
- This overrides any older capacity, Compose, QA, or worker-coordination wording below: budget one login worker only; do not use `docker compose --scale login-worker`; implement no cross-worker advisory-lock protocol.

### Required Reliability Invariants
The following are release blockers for the internal deployment and must be implemented and verified even if the rest of the distributed-state-machine hardening is simplified:
- **Non-predictable SSO credentials:** Newly created SSO users receive cryptographically random passwords; the plaintext is retained only as encrypted automation material when needed, is never rendered in Console/logs, and is invalidated on every operator password change.
- **One browser login per identity:** The single worker and fenced claim ensure only one Playwright/device-flow login runs; task generation still prevents sequential stale work from overwriting newer credentials.
- **No stale token overwrite:** Every login result is bound to the active account credential version and task generation. Manual token import, task cancellation, account deletion, and a newer refresh invalidate older bindings, so old work cannot overwrite a newer GitHub/Copilot token.
- **Durable login result write-back:** A successful or terminal login result is persisted before proxy write-back. When proxy is unavailable, a durable pending write-back is retried; it is never lost solely because an internal HTTP callback failed.

Out of scope:
- SQLite data export/import, dual write, or backward-compatible startup against existing SQLite volumes.
- Redis, Kubernetes manifests, public-edge/WAF work, or external API/DTO shape changes.
- Horizontal scaling of login workers, multi-worker browser coordination, and login worker lease distribution.
- Changing GitHub/Copilot protocol behavior or replacing Playwright login automation.
- Console `ADMINS_FILE`/`admins.json` persistence, encryption-key rotation, request-stat history, and all backup/restore facilities. Before rotating `LOGIN_JOB_ENCRYPTION_KEY`, operators must drain the login queue and confirm no pending/running task secret exists; the runbook documents this limitation.

## Verification strategy
- Tests-after: add Node/TypeScript integration coverage after introducing the new persistence interfaces and before removing the SQLite implementation. Before repository replacement, run LSP reference discovery for `DB_PATH`, `better-sqlite3`, and `recoverInterruptedTasks` and attach the exact call-site inventory to Task 9 evidence.
- Run all database tests against a disposable PostgreSQL 16 service declared in `docker-compose.test.yml`; never point tests at the production `DATABASE_URL`.
- Validate migrations from an empty database, queue retries/dead letters, multi-process coordination, shutdown behavior, short-TTL retention, and two-replica API routing with agent-run Compose commands and captured logs/SQL assertions under `.artifacts/` (gitignored).
- Continue using workspace typechecks and builds; add a root test command that runs all new integration and unit tests.

## Execution strategy
1. Establish shared dependencies, configuration, migration ownership, and test infrastructure before touching service behavior.
2. Replace repository implementations service-by-service, preserving shared DTOs and HTTP routes while deleting SQLite-specific bootstrap only after equivalent PostgreSQL tests pass.
3. Move login execution into durable queue workers and implement distributed coordination before enabling more than one proxy/worker replica.
4. Add lifecycle, observability, short-TTL retention, and Compose topology last; validate the complete stack from an empty state.
