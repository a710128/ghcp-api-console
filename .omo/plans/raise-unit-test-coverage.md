**What you'll get:** An automated test suite for the whole system that verifies the real behavior of the parts that matter — encryption, login/token bookkeeping, user and account management, request compatibility handling, and the database logic — plus a one-command way to run it all and a coverage report showing roughly four out of five lines of core logic are exercised.

**Why this approach:** Tests are split into a fast tier that runs anywhere and a thorough tier that runs against a throwaway PostgreSQL database (the project already ships one for exactly this), so we can actually prove the database-backed logic is correct instead of guessing with mocks.

**What it will NOT do:** It won't change any of your product code (if a test uncovers a real bug, it gets flagged, not silently fixed). It won't test the web dashboard UI or the browser-automation login. It won't add any CI service files or a new test framework.

**Effort:** Large
**Risk:** Low - test-only work; the main external dependency is having Docker available to run the database tier, and those tests auto-skip when it isn't.
**Decisions I made for you:** Use the project's existing test style (Node's built-in test runner + tsx) rather than adding Vitest/Jest; target ~80% coverage on core logic; run database tests against the shipped Docker Postgres; keep everything test-only. You can veto any of these.

## Scope
### Must have
- A repo-wide test toolchain: `node:test` runner via `tsx`, `c8` for coverage, added to every workspace (`@ghcp/shared`, `@ghcp/database`, `@ghcp/proxy`, `@ghcp/sso`, `@ghcp/login`, `@ghcp/console`) plus a root aggregation command.
- A shared `test-support` helper module providing: fixed 32-byte base64 encryption keys, a Postgres connect+migrate+truncate harness for integration tests, and a `fetch` mock helper.
- Unit tests (no DB, always runnable) for every pure-logic unit enumerated in the Todos.
- Integration tests (real Postgres on :5433 via `TEST_DATABASE_URL`) for the SQL-backed repos, queue, migrations, key-fingerprint validation, advisory locks, and login-task coalescing.
- `c8` coverage config per workspace that excludes wiring/UI/Playwright, achieving ~80% line coverage on core-logic files.
- A README/AGENTS documentation section explaining how to run the unit tier, how to bring up the Docker DB tier, and how to run integration + coverage.
- A final verification wave that runs the full suite and confirms the coverage target.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- NO production/source behavior changes. This is test-only. If a test uncovers a real bug in existing code, record it as a written finding in the test file (a `// KNOWN BUG:` comment + a test asserting CURRENT behavior) and surface it to the user; do NOT modify source to "fix" it in this plan.
- NO tests for: React UI (`src/console/src/web/App.tsx`, `main.tsx`, `web/components/**`, `web/api/**` clients), Playwright `HeadlessPlaywrightAuthStrategy.ts`, `auth/deviceFlow.ts`, `tasks/runner.ts`, `worker.ts`, `debugToken.ts`, `mock-github`.
- NO switch to vitest/jest or any other runner.
- NO CI provider config files (GitHub Actions, etc.) — only a documented, runnable command.
- NO coverage target beyond ~80% line on core logic; no 100% chase; no tests written purely to inflate coverage of trivial getters.
- NO edits to stale SQLite documentation beyond adding the new test-running section.
- NO flaky tests: integration tests MUST be deterministic (own schema/truncate, no shared mutable global state, no reliance on wall-clock ordering).

- Test decision: **tests-after** (locking current behavior of existing code) using **`node:test` + `node:assert/strict`**, executed with **`node --test --import tsx/esm`**; coverage via **`c8`** with an ENFORCED `lines: 80` threshold. **Node 22+ is mandatory** (quoted-glob support); `@ghcp/shared` and `@ghcp/database` MUST be built (`dist/`) before any workspace test runs.
